# Gap analysis: OpenVINO GGML device ("Vulkan fallback"), status 2026-11-13

The design review ([architecture.pdf](architecture.pdf), §12) listed 20 findings, L1–L20, from reading the code of Yamini's branches. Since then the stack has been built on Windows and tested. The main test ran all 34 models of the llama.cpp OpenVINO backend's validated list on ggml's CPU and Vulkan backends, on a Core Ultra 7 268V with an Arc 140V (Lunar Lake): see the [test report](../reports/lunarlake_core-ultra-7-268v/TEST_REPORT.md).

This document gives the current status of each finding, the bugs fixed along the way, and the new gaps the tests uncovered.

Severity, as in the review: **P0** wrong results or memory corruption; **P1** blocks a realistic use case, or a major gap; **P2** robustness, performance or process; **P3** hygiene.

## 1. Fixed since the review

The fixes are in pull requests to Yamini's repositories, listed in [PR_GATEKEEPING.md](../PR_GATEKEEPING.md). Until they're merged, [BUILD.md](../BUILD.md) explains how to build with them.

## 2. The review's findings now

| ID | Finding | Sev | Status | Evidence from testing |
| :-- | :-- | :-: | :-- | :-- |
| L1 | Sliding-window attention: the decoders write one full-causal mask to every window | P0 | **fixed, verified 2026-11-16** | The generator now records the windowed mask in the artifact (`mask_roles`, derived from llama.cpp's own filled mask values at the deepest dump position), the loader maps it onto every alias of the leaf, and the decoder/paged runners leave the cells older than the window at -inf. Verified on gemma-3-4b re-dumped at n_kv=2048 (window 1024): the replay's written mask shows exactly 1024 visible cells at position 1223, byte-structure equal to llama.cpp's REF_OUT oracle; text matches llama-cli at 1288 prompt tokens (".cpp" spam before the fix, "Okay, here's a breakdown…" after), and the collapse at ~1230 tokens that the bug caused is gone. gpt-oss-20b (window 128) artifacts at n_kv=512 carry `mask_roles` window 128. The fix also refuses `swa_full=false` dumps (masks of unequal width) with a clean error instead of an out-of-bounds write. |
| L2 | Weights uploaded again for every compiled model (VLM twice, Whisper three times) | P1 | **fixed, verified 2026-11-16** | The Plugin keeps a mutex-guarded weak registry of uploaded models keyed by (canonical GGML_WEIGHTS path, GGML_BACKEND): the first compile of a pair uploads and registers itself, later compiles build their graph over it with CacheMode::Fresh (shared backend and weights, own KV caches); whisper's cross graph is now built in make_runner over the decoder's upload. Measured on this box: whisper decoder+cross second compile 146 ms/+174 MB → 18 ms/+24 MB; LLM second artifact 27 ms/+29 MB → 6 ms/+8 MB; VLM vlm_decoder after token_embd 20 ms/+13 MB (a ~200 MB re-upload skipped); RELEASE=1 expiry re-uploads identically with no crash; GGML_BUCKETS text is byte-identical (CacheMode::Shared default unchanged). Whisper decode itself is verified at compile level only. |
| L3 | Most of the plugin contract unimplemented | P1 | open | The LLM pipelines work through `compile_model(path)` and GenAI's `InferRequest` and `CompiledModel` constructors. Every load parses the JSON and uploads the weights again; there's no model cache. |
| L4 | One runner and one KV state per compiled model | P1 | **fixed, verified 2026-11-16** | Every infer request now builds its own runner over the compiled model's shared weight upload (make_runner over the L2 base): own KV caches, paged block pool and recurrent state. Proven at the plugin level: a raw two-request test (prefill+decode A, B, decode A again) went from CONTAMINATED (argmax 320→333, max logits diff 6.8) to ISOLATED (diff 0); GenAI two-pipeline runs (stateful + paged, incl. a continuation after the other pipeline ran) stay correct; single-pipeline and bucket texts byte-identical; L2 sharing unchanged. GenAI's chat continuation re-prefills history, which masked the collision at the text level — the raw request test is the decisive evidence. Residuals: all requests share one ggml backend, so concurrent infer() on different threads is unsupported (documented; one optimal request advertised); the template's unused KV/pool costs one set per compiled model. |
| L5 | Paged mode relies on GenAI internals | P1 | **partly addressed (P2.4 negotiated block size + guards, verified 2026-11-27)** | The paged path works on CPU and Intel iGPU (`Vulkan1`), with and without an 8-token `ALL_LOGITS` bucket. P2.4 implemented locally (`openvino.jia` `ggml_plugin_l3` + `openvino.genai.jia`): `PagedDecoderRunner` now advertises `KV_CACHE_BLOCK_SIZE` (configurable via `GGML_KV_BLOCK_SIZE`, default 32) and validates `key_cache.0` layout and `tag <= m_pool_blocks` fail-fast in `sync_forked_blocks`; GenAI's `KVCacheManager` reads `KV_CACHE_BLOCK_SIZE` instead of guessing from device names, zero-initializes new `u8` `key_cache` tail bytes, and rejects `use_cache_eviction` on fixed-capacity device-managed KV caches. Verified 2026-11-27 with `src/ggml_paged/paged_test.cpp` on Llama-3.2-1B-Instruct Q4_K_M on both CPU and `Vulkan1` (`d1` at bs=32 and bs=16, `d1 + d8_all`, eviction fail-fast): 29/29 checks passed on both backends. Residual: CoW detection still relies on `key_cache.0` tag bookkeeping rather than an explicit block-copy notification interface, and the changes are not yet upstreamed in PRs. |
| L6 | Per-architecture host logic in the plugin | P1 | open | Gemma's new `inp_scale_rows` input is architecture-specific. The dumper now stores it as a constant, so the plugin needed no change. That works for any input whose value is fixed for a given graph. |
| L7 | Prefill buckets of 16 tokens or more unusable | P1 | **fixed, verified 2026-11-17** | Root cause: at N_TOKENS ≥ 16 the MLP MUL_MAT's ne[1]=2N crosses Vulkan's offload threshold, the scheduler moves it to Vulkan and inserts repacked-weight copy leaves (`Vulkan0#…#0`) that the capture misclassified as .gguf weights. The dumper now pins the model to the CPU device (`llama_model_params.devices`) + disables op offloading, and a post-dump guard fails loudly if a scheduler copy ever leaks in. Verified: d16/d32/d64 dumps are clean (0 decorated weights) and their logits match the d1 baseline (argmax equal, cosine ≥ 0.992); a 512-token bucket at n_kv=2048 matches d1@2048 (0.9989). TTFT on this box's CPU (1320-token prompt, Qwen3-0.6B): d1 23.0 s, b8 12.3 s, b16 11.4 s, b32 10.7 s, **b64 7.5 s** (the sweet spot; b512@2048 is 9.1 s with a heavier cache). The Vulkan-enabled reproduction build wasn't possible on this box (no SDK) — the mechanism is proven from the scheduler code and the guard is the tripwire. Paged prefill stays capped at ≤32 rows (block size). |
| L8 | Shape-static artifacts | P1 | **fixed, verified 2026-11-17** | The stateful decoder now wraps KV slots in a ring once a sequence passes the artifact's capacity (llama.cpp --ctx-shift semantics: positions stay absolute, the oldest positions are evicted and masked; recurrent models keep the throw). Verified against llama.cpp's ctx-shift state via a raw-decode harness (`ring_ref`): logits at 1312 tokens with a 512-capacity artifact match (argmax equal at every eviction depth from 0 to 800; greedy continuation 16/16 tokens identical; cosine degrades gradually with evictions — FA row-order float noise, not semantics). A multi-row bucket chunk spanning the wrap point masks the positions its own rows overwrite (future-token leak found and fixed). The runner exposes `GGML_KV_CAPACITY` (visible-window size; hard limit for recurrent models). Residuals: chat history RAM grows unbounded (as with ctx-shift); bucket families evict at n_kv minus scratch slots (505 for d1+d8), which llama.cpp cannot reproduce exactly (n_ctx padding), so the bucket path is verified structurally (mask dumps) rather than against the oracle; PLE models untested. |
| L9 | Serialised execution | P2 | open | Not measured: the tests ran LLMs only. Decoder prefill without a bucket also runs one token per graph run; on the Arc 140V that is 3.7× slower than with the 8-token bucket. |
| L10 | Malformed artifacts abort the process | P2 | open | Not tested. |
| L11 | 2 GB limit on Windows | P2 | **fixed** | [#101](https://github.com/ynimmaga/openvino/pull/101). Models up to 7.1 GiB load on Windows. |
| L12 | Coupled to upstream versions | P1 | **confirmed, worse** | Artifacts from llama.cpp b12304 broke the replay twice, once with a crash and once with silently wrong output (§1). Nothing in an artifact records which llama.cpp produced it. |
| L13 | Patched ggml under ggml's usual names | P2 | open | Not hit in these tests. |
| L14 | CPU fallback copies device-resident inputs | P2 | open | Not measured. |
| L15 | No tests, CI, samples or user docs | P2 | **partly addressed** | This repository has a test driver, scripts, a README, a build guide and test reports. Upstream, `END_TO_END.md` still describes the deleted classes, and there is no CI. |
| L16 | Debug hooks always compiled in | P3 | open | `GGML_REF` located the Gemma bug: the first decode step's cosine similarity to llama.cpp was 0, and 0.9999 after the fix. Keep it, behind an explicit option. |
| L17 | VLM path covers LLaVA and InternVL only | P2 | open | Not tested. |
| L18 | Device model: one OpenVINO device, ggml backend chosen by a string | P3 | open | On the Lunar Lake machine, Vulkan lists the Arc 140V twice (`Vulkan0`, `Vulkan1`), and nothing in OpenVINO shows which name is which device. |
| L19 | Silent input binding | P2 | **confirmed** | `inp_scale_rows`, an input the runners don't know, stayed unwritten, and every Gemma model generated padding without an error. A load-time check that each graph input is written by a runner or stored as a constant would have reported it. |
| L20 | Trailing zero op_params replayed as defaults | P3 | open | Latent; not seen. |

## 3. New gaps found by testing

| ID | Area | Gap | Evidence | Suggested fix | Sev |
| :-- | :-- | :-- | :-- | :-- | :-: |
| N1 | GenAI | GGUF models don't stop at their end-of-turn token: GenAI's GGUF path stops only at `eos_token_id`. | Gemma 4 (`<turn|>`, id 106) and the Phi models (`<|end|>`) run past their answers. The test driver's `STOP_IDS=` option works around it. | Detect end-of-generation tokens the way llama.cpp does, and add them to the stop tokens. | P1 |
| N2 | GPU | Gemma-4 E2B and E4B fail at load on the Arc 140V, without an error message. | They run on the CPU, and gemma-4-12B runs on the same GPU. Their per-layer embedding table is a single tensor of 1.8 or 2.2 GiB. | Confirm with the run logs and the driver's buffer limits. Then split the tensor, or keep it on the CPU. | P1 |
| N3 | Prefill | Recurrent models can't use prefill buckets at all, because padding rows would enter their state. | The 4 Qwen3.5 models prefill one token per graph run. | Use a bucket when a chunk fills it exactly, and the 1-token graph for the rest. | P2 |
| N4 | Loader | ggml's CPU backend runs with its default of 4 threads. | The loader never sets it, whatever the core count. On the 8-core Lunar Lake, GGML CPU still decodes 1.6× faster than OpenVINO's CPU plugin; on larger CPUs, 4 threads leave most cores idle. | Set the thread count, by default to the number of physical cores, and make it a property. | P2 |
| N5 | Fallback | No automatic fallback when the GPU can't hold a model; `compile_model` now fails cleanly instead. | The loader allocates every weight on the chosen backend, and with [#102](https://github.com/ynimmaga/openvino/pull/102) a failed allocation throws. | Retry on the CPU backend, or keep the tensors that don't fit on the CPU, and report it. A "fallback" device needs this. | P2 |
| N6 | GPU | An apparent fixed cost of about 8–10 ms per token on the Arc 140V, in both the GGML path and OpenVINO's GPU plugin. | Below about 0.5 GiB, models decode faster on the CPU (granite-4.0-350m: 8.2 ms on the GPU, 6.2 on the CPU). The run was over Remote Desktop. | Measure on a local session. If it persists, profile submission and synchronization. | P2 |
| N7 | GPU | ggml's Vulkan backend creates its shader pipelines on first use. | Cold first tokens are slow. This is also the "per-decode-step cost" with several buckets that the generator's `END_TO_END.md` mentions: warm, TPOT is the same with and without buckets. | Run each graph once in `compile_model`. | P2 |
| N8 | Quality | Only agreement has been checked, not accuracy. | The tests compare output text between paths. `GGML_REF` checked the first decode step against llama.cpp for two Gemma models. | Compare perplexity or benchmark scores with llama.cpp's. | P2 |
| N9 | OpenVINO | OpenVINO's GPU plugin also lists non-Intel OpenCL GPUs, then fails on them. | It lists an NVIDIA GPU through NVIDIA's OpenCL driver, and inference there fails with a Broadcast shape error. | A fallback policy must use OpenVINO's GPU plugin only on Intel GPUs, and ggml's Vulkan backend elsewhere. | P3 |
| N10 | Coverage | GenAI's own GGUF path loads 16 of the 34 validated models. | It rejects 7 for their architecture and 11 for their tensor types. | None for the GGML device, which runs all 34. This is its main value next to the native path. | — |

## 4. Suggested priorities

1. **Make the artifact contract robust** (L12, L19, L6). Record the producer (the llama.cpp version) in each artifact, and check at load that every graph input is bound. An unknown input should fail with a clear message, not produce wrong output.
2. **Prefill performance** (L7, N3). Dump and test 16- to 64-token buckets, and let recurrent models use exactly filled buckets.
3. **Gemma-4 per-layer embeddings on Intel GPUs** (N2).
4. **Stop tokens in GenAI's GGUF path** (N1).
5. **Fallback behavior and defaults**: retry on the CPU (N5), thread count (N4), warm-up at load (N7).
6. **Correctness beyond short prompts**: sliding windows (L1, done 2026-11-16), several requests per model (L4, done 2026-11-16), weight sharing (L2, done 2026-11-16), accuracy (N8).
