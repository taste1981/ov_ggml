# Gap analysis: Issues found during OpenVINO GGUF performance testing (2026-11-20)

**Overview: 20 findings, 3 fixed, 17 open.**

This document records issues uncovered during OpenVINO GGUF performance testing in `llama-work-note`, including correctness and compatibility issues. It excludes issues already documented in the [main gap analysis](GAP_ANALYSIS.md). Finding IDs are local to this document.

Severity, as in the main review: **P0** wrong results or memory corruption; **P1** blocks a realistic use case, or a major gap; **P2** robustness, performance or process; **P3** hygiene.

The [November 20 iGPU results](../reports/arrowlake_core-ultra-9-285k/PERFORMANCE_NOTES.md) reproduce findings 5, 8 and 9 and add findings 17-19. No previously open finding was verified fixed. NPU findings and the controlled CPU quantization check (11) were not retested. Finding 20 comes from a GenAI + Vulkan decode profile on 2026-11-25 and 2026-11-26.

## 1. Fixed since the review

| Problem | Effect | Fix | Where |
| :-- | :-- | :-- | :-- |
| 1: The graph dumper increased `n_batch` but left `n_ubatch` at the default of 512 | llama.cpp split the 1024-token capture into two 512-token microbatches. The dumper wrote nodes from both graphs into one artifact instead of exporting a single 1024-token graph. This also happened on a CPU-only build. | Set `n_ubatch` to at least the requested token count so the capture fits in one microbatch | [ggml-cgraph-generator #5](https://github.com/ynimmaga/ggml-cgraph-generator/pull/5); verified with local generator commit `09420ff` |
| 2: GenAI's GGUF tokenizer ignored `tokenizer.ggml.add_bos_token=true` | GenAI sent a plain-text prompt to Gemma-4 12B without its beginning-of-sequence (BOS) token. The model generated repeated digits rather than answering the prompt. | Prepend the BOS token ID with `CombineSegments` when GGUF metadata requests it. The original fix was verified locally. On November 20, both GenAI paths answered the shortest prompt and reported 6 tokens, matching llama.cpp; the digit-heavy output in finding 9 is on a different path. | Upstream GenAI `d929736c`, integrated locally in `712b5617`; branch update: [ynimmaga/openvino.genai #2](https://github.com/ynimmaga/openvino.genai/pull/2) |
| 3: The OpenVINO GGUF frontend treated KV slot indices as token positions when building the causal mask | NPUW pads the static prefill window on the left. The slot indices of real tokens therefore differ from their sequence positions, and the mask could hide tokens that should have been visible. Qwen3-4B and Llama-3.2-1B produced garbled text. | Derive key positions from `CumSum(attention_mask) - 1` and exclude padded slots. The tested NPU outputs matched CPU outputs without the local workaround. | Upstream OpenVINO `630516e048` (#38358), in `adapt_to_genai.cpp`; branch update: [ynimmaga/openvino #108](https://github.com/ynimmaga/openvino/pull/108) |

## 2. New gaps found by testing

| ID | Area | Gap | Evidence | Suggested fix | Sev |
| :-- | :-- | :-- | :-- | :-- | :-: |
| 4 | NPU | On Intel AI Boost NPU 3720, TinyLlama-1.1B takes longer to process the prompt and generate each token via the OpenVINO GGUF frontend than via OpenVINO IR. | The paths use different weight representations. Controlled changes implicated group-32 layer weights in prefill and the grouped Q6_K output projection (LM head) in decode, but did not explain the entire difference. | Inspect NPUW decompression pattern matching for Q6_K and Q8_0; test per-channel `Q8_0_C` for the LM head. | P1 |
| 5 | Prefill | If the only configured prefill bucket is large, the GGML device runs its full fixed-size graph even for a short prompt. | **Open, reproduced November 20.** The 1024-row bucket still handles the shortest prompts in this configuration. This increases the time to the first token; it is not the recurrent-model restriction on padding (main gap N3). | Include smaller buckets in default configurations and verify that the runner selects the smallest bucket that fits the prompt chunk. | P2 |
| 6 | NPU | The NPU37XX plugin compiler rejected graphs generated by the OpenVINO GGUF frontend for tested Q4_K and Q4_1 models. | Q4_K models and Llama-3.2-1B Q4_1 failed with an unsupported asymmetric u4 `DequantizeOp`. A separate Qwen3-4B Q4_K run with the driver compiler was cancelled before it finished. Requantizing to Q4_0 bypassed the compilation failure. | Check whether the frontend can convert the weights to a representation supported by NPU37XX, or report the unsupported format before compilation. | P1 |
| 7 | NPU | With the shared LM head enabled, NPUW can fail to partition a GGUF graph before inference starts. | For Llama-3.2-1B, the partitioner could not find the `logits` MatMul that uses `token_embd.weight` as its weights. Setting `NPUW_LLM_SHARED_HEAD=NO` bypassed the failure but did not fix the shared-head path. | Check how the partitioner identifies the LM head when it shares weights with the token embedding. | P1 |
| 8 | GPU | The OpenVINO GGUF frontend path can produce garbled output on an Intel integrated GPU with an out-of-order queue. | **Open, reproduced November 20.** Llama-3.2-1B, Qwen3-4B and Qwen3.5-4B Q4_K_M had malformed samples at all four lengths. Llama and Qwen3 returned runs of exclamation marks at prompt 5. An in-order queue avoided the Llama failure in a separate November 19 test; this was a workaround, not a fix. | Compare first-step logits across identical GPU requests and against CPU; trace the execution dependencies in the out-of-order queue. | P0 |
| 9 | llama.cpp | The llama.cpp OpenVINO backend produced malformed or repeated text for a Gemma-4 12B prompt longer than its sliding attention window. | **Open, reproduced November 20.** At nominal prompt 2000 (1934 tokens on llama.cpp), the saved sample contained repeated channel markers and digits and the five runs did not all agree. GenAI + Vulkan did not show that collapse; its separate SWA fix is covered by main gap L1. The cause in the llama.cpp OpenVINO backend is unconfirmed. | Reproduce on the same token IDs and use llama.cpp Vulkan as a reference to find the first divergent decode step. | P0 |
| 10 | NPU | Disabling NPUW's shared LM head can make OpenVINO IR inference fail with an output shape mismatch. | With `NPUW_LLM_SHARED_HEAD=NO`, TinyLlama IR produced logits for all prefill rows, but the declared output expected logits for a single token. The runtime rejected the result. | Check which NPUW graph transformation should select the last token when the LM head is not shared. | P2 |
| 11 | Quantization | The OpenVINO GGUF frontend's tested Q4_K conversion lost precision by storing the weight zero point as an unsigned 8-bit integer. | Qwen3-4B generated a different first token from llama.cpp despite identical prompt IDs. Preserving the zero point as f16 via `OV_GGUF_Q4_K_ZP_F16=1` made the tested CPU output match, but did not change the default conversion. | Retest the current default conversion and compare CPU logits with and without the f16 option. | P2 |
| 12 | NPU | The OpenVINO GGUF frontend and NPUW use incompatible names for KV cache states. | The frontend emits `cache_k_l<N>` and `cache_v_l<N>`. When NPUW restores these states as inputs, they do not match `past_key_values.*`, so `RemoveEmptyKVInputs` fails and compilation stops. Renaming the states bypassed this assertion. | Make the frontend and NPUW agree on how to identify KV cache states. | P1 |
| 13 | GenAI | GenAI can infer the wrong KV sequence axis for models that mix attention and recurrent layers. | For Qwen3.5-0.8B, `get_kv_axes_pos` used axis 2 instead of axis 1, causing a shape mismatch when NPUW concatenated KV tensors. Setting `NPUW_LLM_SEQ_LEN_DIM=1` removed this error. The test did not confirm which `ReadValue` GenAI inspected first. | Infer the sequence axis from an attention KV state rather than the first rank-four state. | P1 |
| 14 | NPU | NPUW can apply the attention KV sequence axis to a recurrent convolution state with a different layout. | Even with the correct attention KV axis explicitly set to 1, Qwen3.5-0.8B failed while concatenating `conv_state_l0`. Correcting KV-axis inference alone therefore did not make the model run. | Identify recurrent states separately and avoid applying attention KV resizing rules to them. | P1 |
| 15 | NPU | The tested NPU driver compiler could not deserialize `GatedDeltaNet` in a Qwen3.5-0.8B subgraph. | On the older experimental branch, registering the OpenVINO extension let GenAI load the model, but the driver compiler still rejected the internal operator with `unsupported opset: extension`. This has not been verified on a newer build. | Retest with the current compiler and check whether OpenVINO can lower the operator before submitting the subgraph. | P1 |
| 16 | llama.cpp | Qwen3-4B Q4_K_M produced invalid output or failed to execute on the llama.cpp OpenVINO backend with Intel AI Boost NPU 3720 on Windows. | With a 512-token context, the first generated token was followed by repeated `?` characters. With a 1024-token context, execution returned `ZE_RESULT_ERROR_OUT_OF_HOST_MEMORY` despite available system memory. The two symptoms have not been traced to a common cause. | Retest with greedy decoding and compare logits against the GGML CPU backend. Investigate the device error separately. | P1 |
| 17 | llama.cpp / iGPU | The llama.cpp OpenVINO backend on `GPU.0` did not always reproduce its own greedy output across runs. | On November 20, Llama-3.2-1B at prompt 250, Qwen3-4B at 1000 and Qwen3.5-4B at 5 had non-identical text across five runs. At Qwen3-4B prompt 5, the saved sample repeatedly gave the wrong completion. No common cause was established; Gemma 12B is tracked separately in finding 9. | Compare prompt IDs and first divergent logits across repeated runs and against llama.cpp + Vulkan. | P0 |
| 18 | llama.cpp / iGPU | Gemma-4 E2B and E4B Q4_K_M crash at the start of generation on the llama.cpp OpenVINO backend. | All four prompt lengths returned Windows access-violation status `0xC0000005` without output. The shortest-prompt logs stop after printing the generation parameters. Both Vulkan paths completed on this iGPU; main gap N2 concerns a different Vulkan load failure on Arc 140V. | Capture the exception stack and locate the first failing call on the OpenVINO backend. | P1 |
| 19 | GPU | GenAI + OV cannot compile Gemma-4 E2B and E4B Q4_K_M with the GGUF frontend on `GPU.0`. | All four prompt lengths failed before generation. The shortest-prompt logs for both models show `ProgramBuilder build failed` and `clBuildProgram` returning `CL_BUILD_PROGRAM_FAILURE` (`-11`). The logs do not establish a common cause with finding 18. | Capture the OpenCL build log and isolate the failing kernel. | P1 |
| 20 | GenAI + Vulkan / iGPU | The GGML device reads logits with the synchronous `ggml_backend_tensor_get`. On a UMA GPU, this makes the CPU copy them directly from uncached Vulkan memory. | **Fix submitted in [ynimmaga/openvino #118](https://github.com/ynimmaga/openvino/pull/118) (commit `099d14d`).** On the Intel iGPU, the asynchronous read lowered Llama-3.2-1B decode TPOT by 1.79-2.20 ms/token (6.0%-7.3%) in both run orders, with matching output token IDs. Qwen3-4B and Phi-4-mini were also faster; RTX 5090 (non-UMA) showed no change. Code path, data and setup: [finding 20 report](../reports/arrowlake_core-ultra-9-285k/20-LOGITS_READBACK_AB.md). | Read through `ggml_backend_tensor_get_async` on the backend that owns the tensor, followed by `ggml_backend_synchronize`, as llama.cpp does. ggml then copies the logits on the GPU into its host-cached staging buffer before the CPU reads them, with no ggml patch. | P2 |

The Qwen3.5-4B GenAI + Vulkan exit is covered by [main gap N3](GAP_ANALYSIS.md#3-new-gaps-found-by-testing): the runner rejects the 1024-row prefill graph for recurrent models. No one-token-only retest was run. The two smaller Gemma models completing on this iGPU do not verify a fix for main gap N2 on Arc 140V.
