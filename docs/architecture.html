1. Summary

  • What. GGUF models execute on ggml backends (Vulkan and CPU) through a new OpenVINO device plugin named "GGML". The supported model roles are:
    • text LLMs, both stateful and with PagedAttention / continuous batching;
    • VLMs (LLaVA and InternVL in GenAI);
    • Whisper ASR;
    • text-embedding and reranking encoders;
    • the Qwen-Image 2.1 diffusion transformer.
    The compute graph is the one llama.cpp builds (or whisper.cpp, or stable-diffusion.cpp). It is captured offline into an ov-cgraph-v1 JSON artifact, and openvino_ggml_cgraph_loader replays it at runtime with ggml. The plugin wraps every artifact in a runner, which exposes the input/output contract of the equivalent OpenVINO model: input_ids/attention_mask/beam_idx → logits with KV state for a stateful LLM, or key_cache.N/block_indices/past_lens → logits for PagedAttention, and so on. Existing GenAI pipelines therefore run on it, through new constructors that take an already compiled ov::CompiledModel.
  • What it is not.
    • Not an ov::Model executor. The device compiles artifact paths only: core.compile_model("decoder.json", "GGML", {{"GGML_WEIGHTS", "model.gguf"}}). compile_model(ov::Model) throws and query_model returns nothing. Export/import is not implemented, and AUTO/HETERO cannot use the device.
    • No llama.cpp at runtime. The only new runtime dependency is standalone ggml (v0.23.0, with two local patches).
  • Why (from the code, comments and commit history):
    • Device reach through ggml's Vulkan backend.
    • Architecture coverage and numerics defined by llama.cpp's own graph builders, without porting each architecture to an OpenVINO builder.
    • The full GenAI surface without parallel classes: tokenizers and chat templates from the .gguf, Sampler, the continuous-batching scheduler, streamers and parsers.
  • Status.
    • A prototype spread over three forks, OFF by default.
    • The plugin path has no tests, CI, samples or user documentation, and no performance data.
    • Code comments name many architectures the runners and loader handle (Llama-4, Mistral-3, DeepSeek-2, Qwen3.8-Flash-Next, Gemma-3n, Granite, Mamba/RWKV, BERT-family and T5 encoders, PLaMo-2, PrismML Ternary-Bonsai, Qwen-Image 2.1). There is, however, no published verification matrix for this snapshot.
  • Since the previous review (§16.3):
    • The integration moved from three GenAI-side Ggml*Pipeline classes to a real OpenVINO plugin, plus "construct from CompiledModel" entry points in the standard pipelines.
    • Continuous batching, embeddings, reranking and a diffusion transformer were added.
    • Loader op coverage grew from 26 to 67 ggml ops: MoE, SSM/RWKV, gated delta net and DeepSeek indexer ops.
    • Per-op CPU fallback was added.
    • Four of the earlier review findings are fixed: windows above 256, N× memory per prefill bucket, quantized token embeddings, and M-RoPE.
  • Main findings on this snapshot (§12):
    • Sliding-window (SWA/iSWA) decoders receive one full-causal mask for every attention type, so sliding-window layers attend beyond their window. For gpt-oss (window 128) this happens on any prompt longer than 128 tokens (L1).
    • Every compiled model uploads all weights of its .gguf. A VLM holds the LLM twice and Whisper holds its weights three times (L2).
    • The plugin skips most of the OpenVINO plugin contract (L3).
    • Per-architecture host logic accumulates inside the runners (L6).
    • PagedAttention is emulated through GenAI cache-manager internals (L5).
    • Prefill buckets of 16 tokens or more still cannot be dumped (L7).

Decisions requested from reviewers

  1. Plugin contract. Should OpenVINO accept a device that compiles artifact paths and never sees an ov::Model, as a documented exception? Or must the artifact travel inside an ov::Model (a pass-through op), so caching, query_model and tooling keep working (§15.1)?
  2. GenAI surface. Should the device-agnostic "construct from CompiledModel" constructors become public API? Should a manifest-driven path, LLMPipeline(dir, "GGML"), be added so llm_bench, WWB and samples work unchanged?
  3. Contract ownership. Who owns the artifact format and its compatibility with llama.cpp and ggml? That now includes the input semantics hard-coded in the runners.
  4. Priorities. Correctness and memory first (L1, L2, L7), then a benchmark gate against llama.cpp Vulkan and the OpenVINO GPU plugin, then coverage (§14).

3. Goals and non-goals

Goals (as implemented)

  1. G1 Run GGUF text, vision-language, speech, embedding and image-generation models on any ggml backend, through the standard OpenVINO API (ov::Core, device "GGML") and the existing GenAI pipelines.
  2. G2 The graph topology is llama.cpp's own (or whisper.cpp's, or stable-diffusion.cpp's), with none of those projects present at runtime. The runtime dependency is limited to standalone ggml.
  3. G3 Reuse all of GenAI above the model:
    • tokenizer and chat template from the .gguf;
    • Sampler;
    • the continuous-batching scheduler and block manager;
    • streamers and parsers;
    • VLM and Whisper pre- and post-processing.
  4. G4 Isolation:
    • OFF by default.
    • ggml is linked by the loader only.
    • GenAI carries no GGML build flag and no ggml types. The one device-specific branch is Qwen-Image's ggml.json hook.
  5. G5 Numerical parity with llama.cpp wherever the same ggml kernels run, checkable node by node (REF_OUT + GGML_REF).
  6. G6 GGUF-only model directories: the tokenizer is built from GGUF metadata (SentencePiece, Unigram, WordPiece, BPE).

Non-goals (current iteration)

  • Compiling an ov::Model on GGML; participating in AUTO, HETERO or MULTI; model caching (export/import).
  • Dynamic shapes. Each artifact is fixed to one (n_tokens, n_kv), one image size, or, for the DiT, one (prompt length × image size).
  • Beam search or n > 1 on the stateful path; these need the paged runner.
  • LoRA, speculative decoding and prompt lookup on the compiled-model paths.
  • Python/JS bindings for the new constructors, samples, tests.
  • Multi-GPU or partial offload. There is only per-op CPU fallback.

4. Architecture overview

Three repositories and one contract between them, the ov-cgraph-v1 artifact. The producer shares no code with the consumers. At runtime the application compiles artifacts on the "GGML" device and hands the compiled models to GenAI pipelines.

4.1 Key design decisions

KD1. Capture the topology offline, through each project's own graph builder

  • llama.cpp and mtmd: one ordinary decode with a cb_eval callback.
  • whisper.cpp: compiled into the dumper, because it has no hook.
  • stable-diffusion.cpp: a capture patch to its GGMLRunner, the first producer that modifies an upstream project.

Consequence: an artifact reflects that project's choices for exactly one configuration: flash attention, KV type, token count, number of output rows, and window.

KD2. Artifacts hold topology; weights are resolved by GGUF tensor name at load

The .gguf stays the single weight store. Values travel in the artifact only for things the file does not contain: generated Hadamard matrices, PrismML rotation tables, and the vision tower's index inputs.

KD3. The executor is an OpenVINO device plugin that compiles artifact paths

ov::Core, plugin registration, properties, infer requests and variable state come for free. Every ov::Model-centred feature does not apply: query_model, model caching, HETERO/AUTO, and graph transformations. The compiled model publishes a signature ov::Model: Parameters → one opaque GgmlGraph op → Results.

KD4. Runners: one OpenVINO-shaped interface per model role, chosen from the artifact's input names

A runner converts OpenVINO-style inputs into the graph inputs llama.cpp would have filled: token ids, positions (including M-RoPE streams), KV slot indices, masks (including ALiBi biases), attention temperature, n-gram embedding indices, T5 relative buckets. In effect the runners own a re-implementation of llama.cpp's host-side input code (llm_graph_input_*::set_input) for every architecture they support.

KD5. Shape-static graphs, grouped into graph sets that share one backend, weights and KV cache

A graph set is the main artifact plus GGML_BUCKETS (more token counts and windows). The extra artifacts are built with from_cgraph(json, base). Their cache_* leaves bind to the base cache, or to a view of its first slots. Each forward pass uses the smallest token count that fits, then the smallest window that holds every slot it touches.

KD6. A host-owned, slot-addressed KV cache

SET_ROWS writes K/V at slot indices chosen by the runner, and what a row may attend to is decided only by a host-built mask. Stateful truncation, padding rows, window buckets and PagedAttention emulation are therefore host logic with no graph change.

KD7. PagedAttention by emulation

The ggml cache is GenAI's block pool: block b maps to slots [(b+1)·32, (b+2)·32). GenAI's key_cache.0/value_cache.0 tensors carry only bookkeeping: one owner tag per block, which reveals copy-on-write forks. The scheduler, block manager, prefix sharing and sampling stay unmodified GenAI code.

KD8. GenAI integration: "construct from a compiled model"

The new constructors are device-agnostic. GenAI never parses an artifact, except the Qwen-Image ggml.json hook; the application compiles artifacts itself. This removed the three sibling classes and their duplicated generation loops.

KD9. Single backend by default, per-op CPU fallback only when needed

If the chosen backend rejects a node (ggml_backend_supports_op), the graph is allocated through ggml_backend_sched with the CPU backend as a second backend. Otherwise it uses ggml_gallocr on one backend, as before.

KD10. Tokenizers from GGUF metadata only

GenAI builds OpenVINO tokenizer graphs from the GGUF vocabulary, scores, merges and token types, without reading tensors. GGUF files whose tensor types GenAI's own GGUF reader cannot dequantize still tokenize.

5. Offline graph capture: ggml-cgraph-generator

These are standalone tools, built against a llama.cpp checkout (LLAMA_CPP_DIR) and optionally a whisper.cpp checkout (WHISPER_CPP_DIR), plus a patch for stable-diffusion.cpp. They are the only place those projects appear in the whole system.

5.2 dump_vision: VLM vision tower

Unchanged in mechanism: mtmd runs with the same callback, its warm-up encode is disabled, the capture is reset after clip_init's flash-attention probe, and only the last tile of a tiled image is kept. New: the tower's index inputs, positions (positional-embedding rows) and patches (which rows survive a class token), depend only on the resolution. They are now embedded as constants, so a runtime needs no knowledge of each projector's convention. Image preprocessing is still not captured. With the plugin, GenAI's own per-model preprocessing (LLaVA, InternVL) feeds the vision runner (§9.3).

5.3 dump_whisper: speech recognition

whisper.cpp has no cb_eval and keeps its graph builders file-static, so the tool #includes whisper.cpp and walks the built graphs without computing them. The decoder's KV store is rewritten into SET_ROWS form (Fig. 5). Two switches are new:

  • SPLIT_CROSS=1: the encoder artifact stops at the encoder output, and the cross-attention K/V projection becomes <prefix>.cross.json, with embd_enc as its input. This is the encoder/decoder split an OpenVINO-style Whisper pair needs (input_features → last_hidden_state).
  • CROSS_QK=1: each decoder layer's cross-attention scores (scale·Q·K) become named outputs, cross_attention_qk_scaled_scores_<l>. GenAI's word-timestamp code reads these.

5.4 stable-diffusion.cpp: the Qwen-Image 2.1 transformer

stable-diffusion.cpp/capture-cgraph.patch hooks GGMLRunner. With OV_CGRAPH_OUT=<file> (and optionally OV_CGRAPH_RUNNER / OV_CGRAPH_CALL), it writes the n-th graph of a runner as an artifact. It also names the DiT inputs in qwen_image_2_1.hpp: dit_latent, dit_context, dit_pe, dit_timestep, dit_mask_0. Every other input is baked in as a constant. make_dit_artifact.sh runs sd-cli for one Euler step to trigger the capture. documented The patch calls itself "a fixed-input proof of concept". It needs one artifact per (prompt token count × image token count).

Contract gaps a reviewer should weigh (all but the last were raised in the previous review).

  • No producer metadata: llama.cpp / whisper.cpp / sd.cpp commit, ggml version and dump flags are not recorded.
  • No schema, and no evolution rules for v1.
  • op_params are replayed positionally against the runtime's pinned ggml (v0.23.0). The producers are newer: the loader already re-expresses two ops the pinned ggml lacks (DSV4_HC_PRE, LIGHTNING_INDEXER) with plain ops.
  • Input roles and the cache_ prefix depend on upstream naming conventions.
  • New: how each input must be filled is no longer described anywhere in the artifact. It lives in runner code (KD4), for three upstream projects plus a patch.

7.8 Other runners

  • Vision / token embeddings. The vision graph is static for one square tile, so N tiles mean N graph runs. The token-embeddings graph is the single GET_ROWS cut out of the decoder (DUMP_TOKEN_EMBD), run once per prompt token. Ids beyond the GGUF vocabulary (llava-hf's <image>, <pad>) produce zero rows, which GenAI then overwrites with image features.
  • Whisper. At the first step of each window (past = 0), the runner computes the cross K/V with the cross graph and copies them into the decoder graph's cache_k_cross/cache_v_cross through the host. The decoder then runs one token per graph. With CROSS_QK=1 artifacts it publishes cross_attention_qk_scaled_scores_<l> outputs, and GenAI switches word timestamps on when it sees them. The runner supports batch 1 and cache_position-driven rewinds.
  • Encoders (BERT, NomicBERT, Jina, ModernBERT, NeoBERT, T5 encoder):
    • One graph per sequence-length bucket. Each sample of a batch runs separately, padded into the smallest bucket that holds it.
    • Positions count real tokens only, so left padding is neutral.
    • ALiBi biases and T5 relative-position buckets are computed on the host.
    • Local-attention layers get a second mask with llama.cpp's symmetric window (|q − k| ≤ window/2). This is the one runner that implements sliding windows.
    • A classifier head (rerankers) yields logits [batch, n].
  • DiT (Qwen-Image 2.1).
    • GenAI's exported transformer interface is kept, so the image pipeline is untouched. The runner only accepts the text-to-image layout: gather_idx, modulation_mask and attn_mask are verified, not forwarded, because the captured graph builds that structure itself.
    • It converts rotary tables into stable-diffusion.cpp's 2×2 matrices, transposes latents to planar layout, and scales the timestep by 1000.
    • The model constants (64 latent channels, 4096 context width, head dim 128) are compile-time constants.
    • Any (prompt length, image size) without its own artifact fails with a message to capture one (L8).

8.6 Validation, failure model, debugging hooks

  • Checked, throws (as before): unknown format, missing weight, dangling id, unknown type, unsupported ops (collected), rebuilt ne ≠ recorded ne, constant size mismatch, oversized write_input, allocation failure. New: the CPU backend is chosen and still cannot run an op.
  • Not checked: which inputs a runner must write; header n_kv against the graph; op_params plausibility.
  • Aborts (unchanged): ggml constructors GGML_ASSERT on incompatible operands before the loader's own checks run. A malformed or version-skewed artifact, which is untrusted input, can terminate the host (L10).
  • Debug hooks (environment variables, active in every build):
    • GGML_REF=<file>: after the first compute(), compares every node with llama.cpp's value from REF_OUT and prints the first divergences (GGML_REF_TOL, GGML_REF_SHOW). It marks every node as an output so that none share buffers.
    • GGML_COMPARE_CPU=<step>: runs that step node by node on the device and on a CPU copy (ggml_backend_compare_graph_backend).
    Both keep their state in function-level statics shared by every model in the process (L16).

9.2 Text generation

  • Stateful. StatefulLLMPipeline(InferRequest, …) has no ov::Model to inspect, so its cache state keeps the defaults: sequence axis 2, no linear-attention cache. That matches what SequenceState reports. In chat mode GenAI re-tokenises the history, trims the cache to the common prefix through get_state/set_state, and sends the remainder with a full-length attention_mask. The runner checks past ≤ cached and fills the masks from attention_mask. Prefix reuse is therefore GenAI's own logic. In the previous design it was a ggml-specific token matcher.
  • Continuous batching.
    • The new ContinuousBatchingImpl(CompiledModel, …) reads KV_CACHE_MAX_BLOCKS when the compiled model advertises it. It asserts num_kv_blocks ≤ max, and replaces 0 with the maximum and cache_size with 0.
    • It then calls initialize_from_compiled_model, the tail factored out of the existing ov::Model path (Fig. 15).
    • The block size comes from a device-name test: "GPU" → 16, otherwise 32 (kv_cache_manager.hpp:110). The runner hard-codes 32 to match.
    • Beam search, parallel sampling and prefix caching follow from the block tables and the copy-on-write tags (Fig. 10). review finding None of them is demonstrated.
    • Cache eviction, sparse attention and XAttention need model inputs the runner does not declare. set_tensor should then fail loudly (to verify).

9.3 VLM

  • VLMPipeline(CompiledModelsMap, …) builds an InputsEmbedder from the compiled models, but only for INTERNVL_CHAT and LLAVA (inputs_embedder.cpp:399); other model types throw. The vision encoder takes requests from the compiled vision_embeddings model, with a queue sized by optimal_number_of_infer_requests, which is 1.
  • text_embeddings cannot have scale_emb merged into a compiled graph. It is therefore applied to the output on the host, and a remote output tensor is rejected.
  • The language model must be stateful with a plain KV cache: cache types are forced to KV, sequence axis 2, and attention_mask starts as {1, 0}.
  • Preprocessing is GenAI's per-model C++, not llama.cpp's clip.cpp. Parity between the two for a given mmproj is assumed, not tested (L17).

9.4 Whisper

WhisperPipelineStatefulImpl(encoder, decoder, config_dir, properties) wraps the compiled encoder and builds a WhisperStatefullDecoder from the compiled decoder. The decoder probes for a cache_position input and for cross_attention_qk_scaled_scores_0; the latter enables word timestamps. Everything else (feature extraction, language detection, timestamps, chunking) is the existing stateful pipeline. Dependency note: config_dir must hold the OpenVINO tokenizer IRs, config.json, generation_config.json and preprocessor_config.json, that is, a Hugging Face / optimum export. The whisper.cpp model supplies only the weights and graph.

9.5 Text embeddings and reranking

TextEmbeddingPipeline(CompiledModel, Tokenizer, Config) runs the compiled model for per-token hidden states. Pooling and normalisation run as a separate CPU model, as GenAI already does on NPU. The post-model now has a dynamic batch dimension and copies the attention mask row by row; before, it assumed batch 1, and the fix also applies to the existing NPU path. add_special_tokens is forced on, because GGUF vocabularies declare BOS/EOS in metadata rather than in the tokenizer graph.

9.6 Image generation (Qwen-Image 2.1)

If <transformer>/ggml.json exists ({"weights": "…gguf", "artifacts": [main, buckets…], "backend": "Vulkan0"}), the transformer is compiled on "GGML" and the text encoder and VAE stay on their OpenVINO devices: a mixed-device pipeline. This is the only place GenAI itself turns a description file into compile_model calls, and it is a working prototype of the manifest approach recommended in §15.1.

9.7 GGUF tokenizers

  • Built from GGUF metadata only (get_gguf_metadata): SentencePiece (llama), Unigram (t5, plamo2), WordPiece (bert), and BPE (GPT-2 / Llama-3 pre-tokenizer families, Gemma 4 raw UTF-8 BPE). SentencePiece models are re-serialised as ModelProto for openvino_tokenizers' SentencePiece ops.

14. Further plan

Everything in this section is a proposal from this review, not the authors' roadmap.

Principles.
  1. Correctness and memory before features (L1, L2, L7).
  2. Measure before investing: a benchmark gate against llama.cpp Vulkan and the OpenVINO GPU plugin.
  3. Make the implicit contract explicit. Input-fill rules and artifact recipes should live in the artifact and a manifest, not in runner code (L6, L12, L15).
  4. Follow OpenVINO conventions where that is cheap (typed properties, caching, device ids). Document the remaining exceptions explicitly (L3, L18).
